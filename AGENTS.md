## 1. Цель и единственная метрика

`rosmol-ai-bot` — grounded RAG-помощник поддержки Росмолодёжи (форумы, мероприятия, ФГАИС, гранты)
для каналов HDE и VK.

**Продуктовая метрика одна:** доля тикетов, полностью закрытых ботом без оператора, за любое
число ходов, по строгому критерию (подтверждённый ответ по существу, а не отсутствие эскалации).

**Текущий подтверждённый baseline:** `30% (15/50, прогон 21.08.2026, directional, CI ≈ 18–45%)`.
Типовые `36% (9/25)`, нетиповые `24% (6/25)`, эскалация `38% (19/50)`.

Запрещено выдавать за конверсию:
- показатель «не эскалировал» (`62%`) — это routing-метрика, часть таких ответов неверна;
- first-turn direct answer из июньских документов (`45,1%`) — другая метрика, не сравнима напрямую;
- результаты calibration-набора — это не holdout.

Любая цифра в отчёте сопровождается: дата, `n`, calibration или holdout, определение критерия.

## 2. Определение готовности на текущий месяц

Работа считается выполненной, когда одновременно верно:

1. Эвристический слой снесён (см. §4), поведение задаётся данными и промптами.
2. Провалы прогона разложены по причинам (см. §5) с числами по каждому слою.
3. Снят замер на замороженном holdout ≥ 200 тикетов с честным доверительным интервалом.
4. `docs/CURRENT_STATE.md` содержит актуальный baseline и следующий шаг.

**Достижение 60% в определение готовности не входит.** Целевая цифра — следствие исправления
данных, а не задача разработки. Не оптимизируй код под неё.

Если задача не двигает ни один из четырёх пунктов — она вне scope. Скажи об этом и остановись.

## 4. Главный запрет: никаких эвристик

**Запрещено добавлять в `src/` любую из следующих конструкций:**

- новые регулярные выражения по русскому тексту запроса или ответа;
- новые списки маркеров, алиасов, стоп-слов, групп эквивалентности, совместимых категорий
  (`*_MARKERS`, `*_ALIASES`, `*_RE`, `*_GROUPS`, `*_COMPATIBLE_*`);
- расширение существующих списков такого рода даже на один элемент;
- новые ветки `if` по конкретной формулировке, форуму, смене или мероприятию;
- хардкод-ответы под конкретный кейс.

Причина: этот слой уже вырос до ~13 000 строк (`generate.py` 4296, `analyze.py` 2945,
`rerank.py` 2002, `question_utils.py` 1627, `response_profiles.py` 1100) и вышел на плато.
Каждое новое правило снижает отлаживаемость и не повышает метрику.

**Если кейс невозможно закрыть без такой конструкции — он не является задачей разработки.**
Заведи его как дефект данных или промпта по §5 и остановись. Не обходи запрет.

Правило «делай минимальное изменение» из прежней версии файла отменено: именно оно порождало
точечные эвристики. Правильное изменение — минимальное **в слое причины**, а не минимальное в коде.

## 5. Протокол работы с провалом

Любой провалившийся кейс перед исправлением классифицируется ровно в один слой:

| Код | Слой | Признак в трейсе | Кто чинит |
|---|---|---|---|
| `D1` | Нет факта в KB | нужный чанк отсутствует в seed | контент-команда, Yonote |
| `D2` | Факт разорван между чанками | факты в разных чанках без `parent_chunk_id` | контент + структура KB |
| `D3` | Retrieval не нашёл | чанк есть, но не в кандидатах | embedding, метаданные, фильтры |
| `D4` | Rerank отранжировал ниже порога | чанк в кандидатах, но score < порога | пороги, калибровка |
| `D5` | Не тот аспект / binding | найден верный чанк, ответ про другое | промпт, метаданные аспекта |
| `D6` | Генерация | контекст верный, ответ плохой | промпт |
| `D7` | Политика ответа | эскалация или уточнение неуместны | промпт, правила §7 |

Разрешённые способы исправления: **данные, метаданные, промпт, пороги.** Код `src/graph/` —
только если сломана механика (баг), а не поведение.

Выход разбора — таблица «код слоя → количество кейсов», а не список индивидуальных фиксов.
Сначала разбираем весь набор, потом чиним самый массовый слой. Не чинить кейсы по одному.

## 6. Архитектурные инварианты

- Backend: FastAPI, асинхронные адаптеры каналов и webhook.
- Оркестрация: LangGraph — анализ, retrieval, rerank, generation, verification, response.
- Поиск: Qdrant, `bge-m3`, `bge-reranker-v2-m3`, metadata filters, source-aware rerank.
- Данные: PostgreSQL — trace и долгосрочная память; Redis — сессия и кэш.
- LLM: Cloud.ru, GigaChat 10B для типовых, Max для сложного синтеза.
- Ответ без опубликованных подтверждающих чанков запрещён.
- Yonote — только чтение. Проект ничего в Yonote не создаёт и не изменяет.
- Приоритет фактов: опубликованный Yonote → проверенные XLSX/DOCX-чанки → уточнение или
  контролируемая эскалация. Ответы операторов — материал для gap analysis, не источник фактов.

Изменение любого инварианта — отдельное решение в `docs/DECISIONS.md`, не побочный эффект задачи.

## 7. Поведение бота

- Мероприятие не указано, а ответ от него зависит → уточняющий вопрос.
- Вне тематики, провокации, бессодержательная ругань → короткий scope-note без оператора.
- Ругань вместе с понятным вопросом → игнорировать ругань, ответить по существу.
- Прямая просьба об операторе, персональный статус, повторная техпроблема, отсутствие
  подтверждённых данных → контролируемая эскалация с точной причиной.
- Суицид, насилие, травля, опасная ситуация → немедленная safety-эскалация без LLM.
- Обращение на «ты», tone of voice источника, если это не ухудшает ясность.
- Число уточнений само по себе не является причиной эскалации.

## 8. Запрет на разрастание инфраструктуры

Без явной отдельной задачи **запрещено создавать**:

- новые eval-фреймворки, harness, suite и раннеры (их уже достаточно);
- реестры датасетов, provenance-слои, cost governance, stage funnel;
- новые файлы в `docs/`;
- новые обёртки над существующими скриптами.

Причина: за последние две недели в проект добавлено ~9 200 строк инфраструктуры измерения
и ноль строк продуктовой логики. Инструменты измерения считаются достаточными.

Если для задачи не хватает инструмента — сначала напиши, какого именно и почему существующий
не подходит, и дождись подтверждения.

## 9. Правила для скриптов и диагностики

Прямое следствие инцидента 21.08.2026 (`reason=global_analysis_failed` вместо диагностики):

- Любой обработчик ошибки печатает: **что запускалось, на каком шаге упало, точный stderr/код
  возврата.** Односложные коды провала без контекста запрещены.
- Bash-скрипты не генерируются склейкой из PowerShell-контекста. Скрипт пишется в файл, проверяется
  `bash -n`, затем запускается. Смешивание синтаксиса Python и shell в одной строке — дефект.
- Перед прогоном — `docker compose ... --remove-orphans`. Контейнеры с именами прошлых провалов
  не накапливаются.
- Провал вспомогательного шага (`postflight`, запись метрик) не отменяет и не скрывает результаты
  основного прогона. Результаты сохраняются первыми.
- Тяжёлый eval не перезапускается без сформулированной гипотезы и критерия успеха.

## 10. Данные и секреты

- Никогда не выводить и не коммитить `.env`, токены, пароли, SSH-ключи, API keys, DSN.
- Сырые тикеты HDE и производные приватные данные — только в `data/private/`; не в Git,
  не в Docker image, не на сервере.
- В Git — только обезличенные, вручную проверенные eval-кейсы и агрегаты.
- Операторские ответы не индексируются автоматически как факты.
- Calibration и holdout не смешиваются. Исправленный кейс остаётся regression-тестом, но не
  доказывает обобщение.

```powershell
.venv\Scripts\ruff.exe check .
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe scripts\index_kb.py --validate-only
```

Массовые прогоны — через локальный или server-local `/ask`, не через HDE/VK.
HDE: лимит 300 RPM, бан 20 минут. Бот не используется как нагрузочный транспорт.

## 12. Когда остановиться и спросить

Останавливайся и пиши мне, не продолжая работу, если:

- закрыть кейс можно только эвристикой (§4);
- задача требует нового инструмента или документа (§8);
- нужно менять production-конфиг, миграцию, полную индексацию, KB или откат;
- одновременно меняются KB, routing, пороги и промпты — причину изменения качества будет
  не отделить;
- задача не двигает ни один пункт определения готовности (§2);
- инструкция противоречит фактическому состоянию кода или `CURRENT_STATE.md`.

Молча выбрать «безопасный» обходной путь хуже, чем остановиться. Конфликт инструкций —
всегда повод спросить, а не додумать.

## 13. Git и deployment

- Основная ветка `master`, репозиторий `artemxdata/rosmol-ai-bot`.
- Push не означает, что изменение применилось на сервере.
- Deployment выполняет человек. Агент готовит commit, push и точные безопасные команды.
- Сервер работает только на чтение: `git pull` и `git checkout <SHA>` развёрнутого релиза.
  Commit, merge, branch и push на сервере запрещены. Чекаут сервера всегда совпадает с SHA
  запущенных образов.
- После deployment сверить commit, `/ready`, Qdrant count, trace, результат smoke.
- Не отменять чужие изменения, не использовать destructive Git-команды.
- Admin token не выводить в команды, логи и документы.

## 14. Handoff

Перед завершением длинной задачи или переходом в новый чат обнови `docs/CURRENT_STATE.md`:

- дата и commit;
- что сделано и проверено;
- **текущий baseline: значение, n, calibration/holdout, дата;**
- что выполняется сейчас;
- точный следующий шаг — одним предложением, одним действием;
- результаты тестов;
- открытые риски.

`CURRENT_STATE.md` — рабочий файл на 100–150 строк. Он не летопись. Устаревшие разделы удаляются,
а не дописываются.
