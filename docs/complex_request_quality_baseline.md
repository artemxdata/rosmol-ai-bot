# Базовая линия качества на сложных реальных запросах

**Зафиксировано:** 15 июля 2026

## Цель

Главная продуктовая цель — повышать долю сложных обращений, которые бот полностью закрывает
подтверждённым ответом без оператора за любое число сообщений. Зелёный regression suite нужен
как защита от поломок, но не заменяет измерение конверсии на свежих обращениях.

В работе обязательно учитываются:

- `Тесты бота Росмола.xlsx` — ручные тестовые формулировки и оценки поведения;
- `Сложные_запросы_июнь.xlsx` — 478 отобранных сложных обращений;
- обезличенный полный июньский массив операторских пар;
- опубликованный Yonote и проверенные XLSX/DOCX-чанки как единственные источники фактов;
- новые независимые обращения операторского теста как holdout.

Сырые XLSX, тикеты и подробные производные отчёты остаются в ignored/private-областях и не
коммитятся. В Git сохраняются только агрегаты, обезличенные вручную проверенные regression-кейсы
и решения.

## `Тесты бота Росмола.xlsx`

Фактическая структура:

- 117 первичных вопросов и 29 строк-продолжений — всего 146 тестовых ходов;
- 146 сохранённых ответов;
- 144 ручные оценки;
- категории включают размытые запросы, вопросы про бота, провокации, короткие сообщения,
  multi-intent, жизненные ситуации, негатив и разговорные формулировки.

Историческое распределение оценок: `1: 26`, `2: 18`, `3: 36`, `4: 26`, `5: 38`.
Средняя оценка — около `3.22/5`; `44/144` (`30.6%`) получили 1–2, а `80/144` (`55.6%`) — не
выше 3. Это подтверждает, что workbook нельзя считать закрытым только по текущему pre-pilot gate.

Трассировка в текущий versioned test surface:

- 28 уникальных первичных вопросов имеют точные case IDs в
  `eval/cases/pre_pilot_adversarial.json`;
- это `28/117` (`23.9%`) первичных вопросов или `28/146` (`19.2%`) всех тестовых ходов;
- для 118 ходов нет доказанной цепочки `строка workbook -> case ID -> expected behavior -> split`;
- похожие unit/eval-парафразы существуют, но без provenance manifest не считаются точным
  покрытием workbook.

Это подсчёт точных формулировок, а не semantic coverage: часть отсутствующих строк может быть
покрыта эквивалентными unit-тестами. Но без явной связи «исходная строка → case ID → expected
behavior» считать весь workbook доказанно учтённым нельзя.

## `Сложные_запросы_июнь.xlsx`

Workbook содержит 478 обращений на листе `Все сложные` и отдельный top-20. Все 478 были
прогнаны локально через `/ask` без semantic cache.

Полный импорт и результаты 478 обращений находятся только в ignored/private-артефактах.
Версионируемый `eval/ask_cases_june_regression.json` содержит 11 связанных парафраз, но ни одна
не совпадает с 478 исходными формулировками дословно. Из исходных 478 ровно 5 пересекаются с
`Calibration 200`, ни одна — с `Holdout 100`; поэтому этот прогон нельзя считать полностью
независимым holdout.

Зафиксированный результат:

- прямой подтверждённый автоответ: `223/478` (`46.7%`);
- уточнение без немедленного оператора: `140/478` (`29.3%`);
- передача оператору: `115/478` (`24.1%`);
- первый ответ без нагрузки на оператора, включая уточнения: `75.9%`.

Уточнение не является закрытым тикетом. Поэтому `75.9%` нельзя называть итоговой конверсией без
проверки следующего хода пользователя.

## Полный июньский массив

В приватном pipeline сохранены 3348 обезличенных пар, из них 3295 текстовых запросов запускались
через `/ask`; 53 пустых/attachment-only строки учтены отдельно.

Последний агрегированный аудит перед текущим release candidate:

- прямой автоответ: `1485/3295` (`45.1%`);
- удержание без оператора, включая уточнение: `2875/3295` (`87.3%`);
- передача оператору: `420/3295` (`12.7%`);
- прямой ответ с источником: `1460/3295` (`44.3%`);
- проверяемое golden-подмножество: `394/577` (`68.3%`) прямых ответов с источником.

По сравнению с одной из предыдущих итераций прямое закрытие снизилось, а число немедленных
передач оператору уменьшилось за счёт уточнений и fail-safe поведения. Для главной метрики это
не окончательная победа: требуется доказать multi-turn closure на свежих диалогах.

## Calibration и holdout

- `Calibration 200`: прямой ответ без оператора `137/200` (`68.5%`), 55 уточнений, 8 controlled
  escalations; все 137 автоответов имели cited source IDs.
- `Holdout 100`: набор сформирован и структурно валиден, но не запускался для настройки и не
  является опубликованным доказательством качества.
- Полный pre-pilot suite `passed=true` является regression/calibration gate, а не независимой
  оценкой конверсии.

## Источники текущего runtime

На сервере и в seed находятся 2186 опубликованных чанков:

- Yonote — 1436 (`65.7%`) из 110 документов, выгрузка от 14 июля 2026;
- проверенные XLSX — 714 (`32.7%`);
- проверенные DOCX — 36 (`1.6%`).

Количество Qdrant `knowledge_base = 2186` совпадает с seed. Yonote подключён через ручную
read-only синхронизацию: бот не обращается к Yonote на каждый вопрос и не создаёт, не меняет и не
удаляет документы там. Малое число `cited_sources` в одном trace не означает малую KB: ответ
намеренно цитирует минимальный набор релевантных чанков, а список админки по умолчанию показывает
первые 50 записей.

## Что уже сохранено в Git

- `eval/ask_cases_june_regression.json` — 11 июньских regression-кейсов;
- `eval/cases/operator_policy_regression.json` — 23 operator-policy кейса;
- `eval/cases/pre_pilot_adversarial.json` — 66 adversarial кейсов, включая 28 точных первичных вопросов
  из workbook ручных тестов;
- `docs/operator_golden_calibration.md` — методика и результат Calibration 200;
- `docs/CURRENT_STATE.md` — release gate, текущий RC и следующий шаг.

Подробные ignored-отчёты полезны локально, но не являются надёжным handoff между машинами.
Настоящий документ сохраняет их ключевые агрегаты без публикации приватных данных.

## Текущий вывод и следующий цикл

Текущий RC можно передавать только в ограниченный операторский тест, а не в широкий трафик.
На время теста routing, prompts, thresholds и KB замораживаются. Новые ошибки не исправляются по
одной в реальном времени.

Для каждого свежего тикета собираются:

- закрыл ли бот весь тикет без оператора;
- был ли прямой ответ или успешное разрешение после уточнения;
- обоснована ли эскалация;
- есть ли подтверждающие `cited_sources`;
- есть ли unsupported claim;
- latency и причина незакрытия.

После теста обращения делятся на calibration и новый holdout. Затем выполняется один пакетный
цикл: классификация дефектов → подтверждение источника → минимальная правка → regression →
повторная calibration → однократный holdout.
