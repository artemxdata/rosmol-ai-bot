### Почему это не штатный трафик бота

В тот же момент `docker stats` показывал для контейнеров только мегабайты накопленного network
I/O: у Nginx около `1.32/1.03 MB`, у `app-ml` около `5.72/1.76 MB`, у PostgreSQL около
`83.9/42 MB`, у Qdrant около `114/20.4 MB`. Контейнеры были почти не загружены.

Холодная загрузка `bge-m3` и `bge-reranker-v2-m3` составляет единицы гигабайт и использует общий
persisted cache. Полная индексация также не может объяснить 15.5 TiB: наблюдавшиеся большие
значения `BLOCK I/O` относятся к диску/подкачке, а не к внешней сети. Поэтому аномальный трафик
не объясняется работой RAG, LLM, eval-наборов или индексацией.

## Что пока нельзя утверждать

До ответа Selectel и отдельной форензики нельзя достоверно утверждать:

- каким способом и когда злоумышленник впервые получил доступ;
- какие IP, порты и протоколы были адресатами трафика;
- был ли трафик атакой, проксированием, майнингом с сетевой составляющей или утечкой данных;
- какое семейство ПО использовалось;
- скомпрометирован ли весь аккаунт Selectel, а не только гостевая ОС;
- создан ли пригодный forensic image;
- окончательно ли остановлены начисления и каков их точный размер.

Отсутствуют признаки, связывающие инцидент с ноутбуком пользователя. Это не является полноценной
форензикой endpoint: локальную проверку следует рассматривать отдельно от восстановления сервера.

## Граница доверия: ничего со старого сервера в новый runtime

Старая VM и всё содержимое её файловой системы считаются недоверенными. В новый контур
**запрещено переносить или повторно использовать**:

- образ VM, системные или подключённые диски;
- `/opt`, `/etc`, `/root`, `/tmp`, `/var/tmp`, `/dev/shm`, `/var/lib/docker`;
- старые Docker images, containers, layers, volumes и build cache;
- старый `.env`, shell history, SSH host/user keys и deployment credentials;
- TLS/ACME private keys и сертификатный state;
- Redis dump/session state, runtime-файлы и исполняемые артефакты;
- PostgreSQL/Qdrant данные из старого runtime;
- любой файл с хоста только потому, что он «выглядит нормальным».

Новый runtime собирается только из чистого vendor image и проверенного Git commit. Для
воспроизводимости frozen RC Qdrant пересоздаётся строго из versioned published seed этого commit,
без свежего Yonote Apply. Yonote preview/sync является отдельным последующим content/KB change с
validation, regression и новым handoff.

## Отдельная обязательная задача: перевыпуск секретов

Ротация начата 16 июля 2026 с read-only инвентаря. По подтверждению владельца удалены все
Cloud.ru API keys, старый GitHub server deploy key и все Yonote tokens; новые credentials пока
не создаются. HDE, Selectel и условные внешние интеграции ещё не закрыты.
Полный реестр, статусы и evidence policy ведутся в `docs/secret_rotation_20260716.md`. Перед
созданием нового runtime необходимо считать
раскрытыми и отдельно перевыпустить все секреты, которые могли находиться на старой VM:

- Cloud.ru / GigaChat;
- Yonote read-only token;
- HDE API, webhook и dispatcher credentials;
- admin/API/webhook tokens приложения;
- PostgreSQL, Redis и Qdrant credentials, если они использовались;
- GitHub deploy key/token, если он присутствовал на сервере;
- Selectel/cloud API tokens, если они присутствовали на сервере;
- SSH keys и TLS/ACME private keys;
- `USER_HASH_SECRET`.

Значения секретов не помещаются в Git, команды, тикеты или документы. Ротация
`USER_HASH_SECRET` намеренно создаст новое пространство pseudonym/hash и разорвёт continuity
старых сессий и cohort; при root-компрометации это обязательная мера.

Redis в legacy-конфигурации не имел password, а Qdrant — API key. Их нельзя отмечать как
`rotated`: на clean host создаются новые пустые instances без старых volumes и публичных ports;
добавление auth оформляется отдельным проверяемым infrastructure/security patch.

## План чистого восстановления

1. Не включать и не удалять старую VM/диск до согласования evidence preservation с Selectel.
   Provider-side forensic image/snapshot без запуска гостевой ОС ещё не подтверждён и является
   pending action; такой image никогда не используется как рабочий сервер.
2. Параллельно продолжать Selectel ticket: запросить подтверждение остановки
   трафика/начислений, flow-данные и рекомендации по доказательствам. Ответ провайдера не блокирует
   немедленную secret rotation и создание отдельной чистой VM, но обязателен перед удалением
   старой VM/диска.
3. Параллельно уведомить операторов/владельца HDE о паузе и отключить либо заморозить старое
   webhook rule, чтобы новые обращения не терялись и не считались тестом. Выполнение пока не
   подтверждено.
4. Выполнить отдельную задачу по перевыпуску всех ключей и секретов.
5. Проверить GitHub с доверенного локального устройства: отозвать server deploy credentials,
   проверить repository deploy keys/tokens, account/audit history, неизвестные commits, tags и
   Actions; после проверки зафиксировать trusted commit hash.
6. Оценить, какие операционные и потенциально персональные данные физически находились на VM,
   проверить внешние API audit logs после ротации и определить вместе с владельцем данных, нужны
   ли уведомления. Наличие exfiltration/data breach не считать доказанным без evidence.
7. Создать новую VM из чистого образа провайдера, не из snapshot старого диска.
8. Настроить SSH key-only, запретить password/root login, открыть 22/tcp только доверенным
   адресам/VPN; публично оставить только 80/443.
9. Включить доступные у провайдера egress-ограничения, flow logging и алерты по трафику/CPU.
10. Получить код новым clean checkout только после GitHub audit и сверить trusted commit с
   `origin/master`.
11. До provisioning заменить IP-specific infrastructure configuration старого хоста на новый
   endpoint. Сейчас прежний IP ожидаемо остаётся в `nginx/admin-tls.conf`,
   `nginx/select-config.sh`, `scripts/provision_admin_https.sh`, `tests/test_admin_tls.py` и
   `scripts/build_presentation_readiness.py`; эти значения нельзя применять на новой VM.
12. Создать новый `.env` только из перевыпущенных секретов; выпустить новый TLS certificate.
13. Пересоздать PostgreSQL/Redis/Qdrant и KB с нуля. Старые runtime backup/snapshot не
   восстанавливать.
14. Выполнить preliminary security/runtime acceptance: migrations, `/ready`, published KB count и
    короткий server-local smoke. HDE/operator cohort пока не включать.
15. На чистом runtime воспроизвести feedback Наты, получить content verdict по «Машуку» и
    выполнить один отдельно согласованный regression-first correction cycle. Любой content/KB
    change версионировать и валидировать как самостоятельное изменение.
16. После исправлений выполнить финальный полный server-local suite и короткий реальный HDE
    delivery/deduplication smoke.
17. Только после финального handoff включить новый HDE endpoint и начать новый операторский cohort
    с новой временной границей.

## Влияние на операторский тест

P0 stop-criterion сработал. Cohort, начатый 15 июля, прерван и не является итоговой оценкой
конверсии. Его trace можно использовать только как исторический/предварительный материал после
проверки целостности. Старый и новый cohort объединять нельзя.

Последний зелёный release gate остаётся доказательством поведения зафиксированного кода до
инцидента, но не доказывает безопасность или доступность текущего runtime. Код, routing, prompts,
thresholds и KB в локальном Git из-за инцидента не менялись.
