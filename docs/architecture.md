## 1. Формат извлечения данных из текущего бота

Перед тем как строить новую систему — нужно корректно извлечь контент из config.json.

### Что извлекать

Все слоты с `type: "context"`, у которых в `data.inputs` есть ключ `bot_message`. Это 792 записи — полный корпус ответов бота. Каждый ответ превращается в один JSON-объект.

### Целевой формат одной записи

```json
{
  "chunk_id": "ctx_759",
  "slot_index": 759,
  "slot_name": "Вернуть грантовые средства — легко! 💸",

  "text_raw": "<оригинальный HTML из bot_message>",
  "text_clean": "Вернуть грантовые средства — легко! Просто свяжись с нами: Телефон: 8(495)123-33-44 (доб.1)...",

  "forum": null,
  "forum_normalized": null,
  "topic": "возврат_грантовых_средств",
  "category": "гранты",
  "is_generic": true,

  "has_conditional_logic": false,
  "conditions_summary": null,

  "links": ["reportgrant2024@fadm.gov.ru"],
  "phones": ["8(495)123-33-44"],
  "dates_mentioned": [],

  "valid_from": null,
  "valid_to": null,
  "extraction_date": "2026-06-09"
}
```

### Правила заполнения полей

**text_clean** — убрать `<br>`, `<b>`, `</b>`, HTML-мнемоники, лишние переносы строк. Сохранить эмодзи, ссылки, нумерацию. Не редактировать текст — только чистить разметку.

**forum** — извлекается двумя способами:
- Из имени слота, если паттерн `"Тема. Форум"` (например, `"Трансфер. Машук"`, `"Оплата проезда. Истоки"`)
- Из текста, если есть `форум[еуа]? «...»` (regex: `форум[еуа]?\s*[«"]([^»"]+)[»"]`)
- Если обоими способами не определился — `null`, пометить для ручной разметки

**forum_normalized** — привести к стандартному написанию. Маппинг:
```
"Территория смыслов" | "Территория Смыслов" → "Территория смыслов"
"иВолга" | "Иволга" | "Волга" → "иВолга"
"ТИМ Бирюса" | "Бирюса" → "ТИМ Бирюса"
"На волне" | "На Волне" → "На волне"
"ОстроVа" → "ОстроVа"
"Область будущегоо" → "Область будущего"
```
Полный справочник — 25 форумов (список из анализа конфига).

**topic** — нормализованный идентификатор. Определяется из имени слота и содержания:
```
"регистрация" — подача заявки, сроки, инструкция
"резервный_список" — статус «Резерв»
"отклонение_заявки" — отказ в заявке
"отказ_от_участия" — добровольный отказ
"оплата_проезда" — кто платит за дорогу
"трансфер" — автобусы, точки сбора
"проживание" — палатки, корпуса, условия
"питание" — столовые, фудкорты
"документы" — список вещей и документов
"письмо_вызов" — официальное подтверждение
"письмо_подтверждение" — email после отбора
"возраст" — ограничения по возрасту
"направления" — смены, описания направлений
"волонтёры" — набор волонтёров
"медицина" — медпункт, ОВЗ
"сертификат" — сертификат за участие
"чат_мероприятия" — добавление в чат
"положение" — ссылка на положение форума
"программа" — расписание, артисты
```

**category** — верхний уровень:
```
"форумы" — всё, что привязано к конкретному форуму
"гранты" — грантовый конкурс, заявки, отчётность, возврат
"платформа_фгаис" — регистрация, профиль, пароль, верификация, ID
"общее" — что такое Росмолодёжь, направления, вакансии
"техподдержка" — технические ошибки
"модерация" — нецензурная лексика, оффтоп
"навигация" — приветствие, прощание, переключение на оператора
```

**has_conditional_logic** — `true`, если текст содержит развилки: «если тебе 14-17 лет...», «если из Приволжского ФО...», «если статус Отклонено...». Такие чанки при генерации требуют, чтобы модель учитывала параметры пользователя.

**conditions_summary** — краткое описание условий, если `has_conditional_logic: true`. Например: `"Различается по возрасту: 14-17 лет — корпуса, 18-35 — палатки"`.

### Что ещё извлечь параллельно

**Дерево маршрутизации.** Для каждого context-слота проследить путь в дереве: какой intent ведёт к этому ответу, через какие switch_case проходит. Это даст маппинг `intent → forum → topic → ответ`, который нужен для валидации RAG-пайплайна.

**Промпт LLM-роутера** (слот 2980). Он содержит полную логику маршрутизации с приоритетами: технические > мероприятия > рекомендации > гранты > общее. Эта логика переедет в Query Analyzer.

**Список форумов и их смен.** Вытянуть из промпта LLM-роутера (там есть `{{ promt }}` с полным списком).

### Формат выгрузки

Один JSON-файл (`knowledge_base_seed.json`) — массив записей. Плюс отдельно `routing_logic.md` с промптом роутера и `forums_registry.json` с перечнем форумов и нормализованными названиями.

### MVP-источники базы знаний

На этапе MVP базой знаний считаются три локальных источника:
- `Новый бот Росмол .xlsx` — основная выгрузка ответов, fallback-ответов, примеров интентов и словаря событий;
- `Форум «Российский Север» интенты.docx` — актуальные ответы по форуму «Российский Север»;
- `Фестиваль «Больше, чем путешествие» Интенты .docx` — актуальные ответы по фестивалю «Больше, чем путешествие».

Исходные Excel/DOCX не коммитятся как рабочие документы. В Git хранится нормализованный артефакт `data/knowledge_base_seed.json` и воспроизводимый скрипт сборки.

Правило качества: `text_raw` сохраняет исходный текст ответа, `text_clean` только очищает техническую разметку (`<br>`, HTML-теги, лишние пробелы). Тексты ответов и tone of voice не переписываются и не «дополировываются» до отдельного этапа редакторской правки.

## 2. Целевая архитектура

### Принцип

Текущий бот: **LLM-роутер → дерево → хардкоженный текст.**
Новый бот: **LLM-анализатор → RAG-поиск по метаданным → LLM-генерация по источникам → верификация.**

Ответ всегда формируется из найденных фрагментов базы знаний. Модель никогда не отвечает «из головы».

Для типового простого вопроса с высокой уверенностью reranker бот может отвечать детерминированно:
возвращать текст лучшего опубликованного чанка без вызова LLM. Это сохраняет исходный tone of voice,
исключает перефразирование и снижает стоимость. LLM-генерация используется для составных,
нетиповых и среднеуверенных кейсов, где нужно собрать ответ из нескольких источников.

### LLM-провайдер

В проекте используется **Cloud.ru Evolution Foundation Models**, а не прямой Sber GigaChat API
(`developers.sber.ru`). Это архитектурное правило, чтобы не смешивать разные схемы авторизации и
endpoint-ы.

- Endpoint: `https://foundation-models.api.cloud.ru/v1/chat/completions`
- Авторизация: `Authorization: Bearer <CLOUD_RU_API_KEY>`
- Формат: OpenAI-compatible Chat Completions (`model`, `messages`, `max_tokens`, `temperature`)
- Модель для типовых запросов: `ai-sage/GigaChat3-10B-A1.8B`
- Модель для нетиповых/сложных запросов: `GigaChat/GigaChat-2-Max`
- Переменные окружения: `CLOUD_RU_API_KEY`, опционально `CLOUD_RU_CHAT_COMPLETIONS_URL`,
  `CLOUD_RU_MODEL` или `CLOUD_RU_MODEL_SIMPLE`, `CLOUD_RU_MODEL_COMPLEX`,
  `CLOUD_RU_MODEL_ANALYZER`, `CLOUD_RU_MODEL_JUDGE`
- Стоимость Max на Cloud.ru: входные токены — 569.34 ₽/млн, генерируемые токены —
  569.34 ₽/млн; контекст до 131K токенов
- Не используются: OAuth flow, `GIGACHAT_API_KEY`, `GIGACHAT_ACCESS_TOKEN`, `GIGACHAT_SCOPE`,
  `developers.sber.ru`

### Нода: retrieve

```
┌─────────────────────────────────────────────────────────┐
│              RETRIEVAL PIPELINE                         │
│              (выполняется для КАЖДОГО question)          │
│                                                         │
│  Шаг 1: METADATA FILTER (Qdrant)                        │
│                                                         │
│  Фильтры формируются из JSON Query Analyzer:            │
│                                                         │
│  if forum:                                              │
│    filter += {forum_normalized: forum}                   │
│  if category:                                           │
│    filter += {category: category}                        │
│  filter += {status: "published"}                        │
│  filter += {valid_to >= today OR valid_to == null}        │
│                                                         │
│  Результат: из ~1000 чанков остаётся 15-40.              │
│                                                         │
│  ─────────────────────────────────────────────           │
│                                                         │
│  Шаг 2: HYBRID SEARCH (Qdrant)                          │
│                                                         │
│  По отфильтрованному подмножеству:                      │
│                                                         │
│  Dense search: bge-m3 эмбеддинги (1024-dim)             │
│    Запрос: question.detail                               │
│    → top-10 по cosine similarity                         │
│                                                         │
│  Sparse search: bge-m3 sparse (встроенный)              │
│    Ловит точные совпадения: «Машук», «Таврида»,         │
│    «14-17 лет», «reportgrant2024@fadm.gov.ru»           │
│    → top-10 по BM25-like scoring                        │
│                                                         │
│  Fusion: Reciprocal Rank Fusion (RRF)                   │
│    → top-10 объединённых                                │
│                                                         │
│  Почему bge-m3:                                         │
│  Генерирует dense и sparse представления из одной        │
```

### Индексация

```python

    collection_name="knowledge_base",
    vectors_config={

    },
```

### Жизненный цикл обновления

Два режима: Git (для разработчика) и админ-панель (для редактора).

**Режим 1: Git + CI (для разработчика/Артёма)**

```
1. Редактор правит markdown-файл в Git-репозитории
   (knowledge-base/форумы/машук/оплата_проезда.md)

2. Commit + push в main

3. CI (GitHub Actions):
   - Парсит YAML-фронтматтер (метаданные)
   - Генерирует dense + sparse векторы через bge-m3
   - Upsert в Qdrant
   - Помечает старую версию status: "archived"
   - Запускает eval pipeline (раздел 9)
   - Если eval прошёл — публикация; если нет — блокировка

4. Бот сразу использует новую версию
```

**Режим 2: Админ-панель (для редактора/Насти)**

```
1. Редактор открывает web-интерфейс
2. Выбирает форум и тему из справочников
3. Загружает или редактирует текст ответа
4. Система показывает preview: как текст разобьётся на чанки
5. Редактор проверяет метаданные, правит если нужно
6. Нажимает «Опубликовать»
7. Backend: генерирует векторы, upsert в Qdrant,
   запускает eval на затронутых чанках
8. Если eval прошёл — публикация; если нет — предупреждение
```

Для Qdrant это ничтожная нагрузка. Сервер с 16 GB RAM обработает 100K+ чанков.

## 4. Семантический кэш

Многие пользователи задают одинаковые вопросы: «когда регистрация на Тавриду», «какие документы нужны», «как подать заявку на грант».

### Реализация

```python
# При каждом запросе:
query_embedding = embed(masked_message)
cache_hit = qdrant.search(
    collection="response_cache",
    query_vector=query_embedding,
    score_threshold=0.95,  # очень высокий порог
    limit=1,
    query_filter={"forum_normalized": forum_context}
)

if cache_hit and cache_hit.payload["cached_at"] > (now - TTL_24h):
    return cache_hit.payload["response"]
else:
    response = run_full_pipeline(...)
    qdrant.upsert("response_cache", response_with_embedding)
```

### Инвалидация

При обновлении любого чанка с `forum_normalized = X` — весь кэш для этого форума сбрасывается. При обновлении `is_generic` чанка — сбрасывается весь кэш.

### Эффект

При ~1200 тикетах/мес — ожидаемый cache hit rate 30-50%. ~400-600 сэкономленных LLM-вызовов ≈ экономия ~40% на API.

## 5. Долгосрочная память пользователя

### Принцип

Не полный профиль, а контекст общения. Никаких ПДн в таблице — только hash и тематическая информация.

### Модель данных (PostgreSQL)

```sql
CREATE TABLE user_memory (
    id SERIAL PRIMARY KEY,
    user_id_hash VARCHAR(64) NOT NULL,  -- SHA-256(channel + user_id)
    channel VARCHAR(10) NOT NULL,       -- "vk", "max", "hde"
    last_forum VARCHAR(100),
    last_topics TEXT[],                  -- ["оплата_проезда", "трансфер"]
    turn_summary TEXT,                  -- краткое резюме последнего диалога
    interaction_count INT DEFAULT 1,
    last_interaction TIMESTAMP NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    
    UNIQUE(user_id_hash, channel)
);

-- TTL: удалять записи старше 30 дней
-- Cron: DELETE FROM user_memory WHERE last_interaction < NOW() - INTERVAL '30 days';
```

### Использование

```python
# При первом сообщении в сессии:
memory = db.query(
    "SELECT last_forum, last_topics, turn_summary FROM user_memory "
    "WHERE user_id_hash = %s AND channel = %s",
    (hash(user_id), channel)
)

if memory:
    session.forum_context = memory.last_forum
    session.context_hint = memory.turn_summary
    # Query Analyzer получит: "Пользователь ранее спрашивал про Машук,
    # темы: оплата проезда, трансфер"
```

### Что это даёт

Пользователь неделю назад спрашивал про Машук. Сегодня пишет: «А что с моей заявкой?» Бот понимает, что речь про Машук, и не задаёт уточняющий вопрос.

### Юридическая чистота

`user_id_hash` — это SHA-256 от `"vk:123456789"`. Без маппинга hash → user_id (который нигде не хранится) это не ПДн. В таблице нет ФИО, телефонов, email — только тематический контекст. Пользователь может написать «забудь мои данные» → бот удаляет запись по hash.

### Жизненный цикл документа


### Endpoint authentication

Для production endpoint-ы поддерживают опциональные shared-secret токены:

- `/ask`: `API_AUTH_TOKEN`, заголовок `X-API-Key` или `Authorization: Bearer ...`
- `/webhook/*`: `WEBHOOK_AUTH_TOKEN`, заголовок `X-Webhook-Secret` или
  `Authorization: Bearer ...`

Если токен не задан, проверка отключена для локальной разработки. Секреты не логируются и не
попадают в `request_traces`.

### Request timeout budget

Выполнение LangGraph ограничено `REQUEST_TIMEOUT_SECONDS` (по умолчанию 45 секунд). При
превышении бюджета бот возвращает контролируемую эскалацию `request_timeout`, сохраняет turn,
пишет trace и не кэширует ответ.

```sql
    llm_total_tokens INT DEFAULT 0,
    llm_estimated_cost_rub NUMERIC(12, 6) DEFAULT 0,
    
    -- Результат
    response_text TEXT,
    was_escalated BOOLEAN DEFAULT FALSE,
    escalation_reason VARCHAR(50),
    
    -- Общее
    total_latency_ms INT,
    trace_events JSONB DEFAULT '[]'::jsonb, -- события нод LangGraph: latency, metadata, error
    prompt_version VARCHAR(20),
    error TEXT
);

-- Индексы для аналитики
CREATE INDEX idx_traces_timestamp ON request_traces(timestamp);
CREATE INDEX idx_traces_forum ON request_traces((query_analysis->>'forum'));
CREATE INDEX idx_traces_escalated ON request_traces(was_escalated);
CREATE INDEX idx_traces_model ON request_traces(generator_model);
CREATE INDEX idx_traces_cache ON request_traces(cache_hit);
```

### Что это даёт

**Дебаг конкретного запроса:** открываешь trace по request_id → видишь: что анализатор извлёк из вопроса, какие фильтры применил, какие чанки нашёл (и их scores), какую модель использовал, что верификатор сказал, итоговый ответ.

**Системная аналитика:**

```sql
-- Средняя латентность за день
SELECT DATE(timestamp), AVG(total_latency_ms) FROM request_traces
GROUP BY DATE(timestamp);

-- Процент эскалаций по форумам
SELECT query_analysis->>'forum' as forum,
       COUNT(*) FILTER (WHERE was_escalated) * 100.0 / COUNT(*) as escalation_pct
FROM request_traces GROUP BY forum;

-- Чанки, которые часто находятся, но получают низкий reranker score
-- (кандидаты на переработку)
SELECT chunk_id, AVG(score) as avg_score, COUNT(*) as times_retrieved
FROM request_traces, jsonb_array_elements(reranker_scores) as r(obj)
CROSS JOIN LATERAL (SELECT obj->>'chunk_id' as chunk_id, (obj->>'score')::float as score) parsed
GROUP BY chunk_id HAVING AVG(score) < 0.5 AND COUNT(*) > 10;

-- Cache hit rate по дням
SELECT DATE(timestamp),
       COUNT(*) FILTER (WHERE cache_hit) * 100.0 / COUNT(*) as cache_hit_pct
FROM request_traces GROUP BY DATE(timestamp);

-- Использование LLM-моделей Cloud.ru
SELECT generator_model, COUNT(*), 
       AVG(generation_latency_ms) as avg_latency
FROM request_traces GROUP BY generator_model;
```

### Связь с бот-анализатором в HDE

Бот-анализатор в HDE классифицирует тикеты параллельно (кастомные поля ID=23, ID=29, ID=25). Сопоставление через `user_id_hash + timestamp (±5 мин)` позволяет:
- Сравнить тему: совпало ли `query_analysis.category` с классификацией анализатора
- Проверить: если анализатор ставит «эскалация», а бот ответил сам — проверить quality
- Еженедельный отчёт: расхождения → кандидаты на доработку KB или промптов

## 8. Эскалация и fallback: полная матрица

| Ситуация | Детекция | Действие | Сообщение пользователю |
|---|---|---|---|
| Safety (суицид, угрозы) | Safety detector, ключевые слова + LLM | Мгновенная эскалация, логирование | Безопасный текст + «Передаю специалисту» |
| Нецензурная лексика | Regex (слот 2, уже есть) | Мягкое предупреждение, НЕ эскалация | «Пожалуйста, воздержись от таких выражений» |
| Форум не указан | Query Analyzer: forum=null | Нода clarify | «Уточни, пожалуйста, название форума» |
| Нет релевантных чанков | Все reranker scores < 0.4 | Нода escalate | «В опубликованных материалах нет информации. Передаю специалисту.» |
| Средняя уверенность | 0.4 ≤ score < 0.7 | Ответить + дисклеймер | Ответ + «Рекомендую уточнить у специалиста» |
| Галлюцинация обнаружена | LLM-judge в верификаторе | Удалить ответ → эскалация | «Передаю обращение специалисту» |
| Пользователь просит оператора | Intent detection в Query Analyzer | Мгновенная эскалация | «Переключаю на специалиста» |
| Не по теме Росмолодёжи | Query Analyzer: category="offtopic" | Мягкий отказ, НЕ эскалация | «Это не относится к вопросам Росмолодёжи» |
| Техническая проблема | Query Analyzer: is_technical=true | RAG по техподдержке + предложить оператора | Шаблон (кэш, браузер) + «Если не помогло — оператор» |
| turn_count > 5, нет решения | Session Manager | Предложить эскалацию | «Кажется, вопрос требует помощи специалиста» |
| Повторный вопрос (пользователь недоволен) | Детекция в Query Analyzer по session | Эскалация | «Передаю специалисту для более детальной помощи» |

## 9. Eval pipeline: автоматическое тестирование качества

### Golden set

100 тикетов из HDE с эталонными ответами:

```json
{
  "id": "eval_001",
  "question": "Мне 17 лет, я попал в резерв на форум Машук, письмо не пришло. Что делать?",
  "expected_forum": "Машук",
  "expected_topics": ["резервный_список", "письмо_подтверждение", "возраст"],
  "expected_chunks": ["ctx_852", "ctx_824", "ctx_848"],
  "reference_answer": "...",
  "source": "hde_escalated",
  "difficulty": "complex"
}
```

Источники:
- Бот-анализатор: тикеты с высокой эскалацией (текущий бот не справился)
- Бот-анализатор: тикеты с корректными ответами (baseline)
- День молодёжи: составные вопросы, обрушившие конверсию

### Метрики

| Метрика | Что измеряет | Порог |
|---|---|---|
| Retrieval Recall@5 | Нашёл ли RAG нужный чанк в top-5 | ≥ 85% |
| Answer Faithfulness | Нет ли утверждений вне источников | ≥ 95% |
| Answer Completeness | Ответил ли на все подвопросы | ≥ 80% |
| Escalation Precision | Оправданы ли эскалации | ≥ 90% |
| Latency p95 | Скорость ответа | < 3000ms |

### CI интеграция

```yaml
# .github/workflows/eval.yml
name: KB Eval
on:
  push:
    paths: ['knowledge-base/**']

jobs:
  eval:
    runs-on: self-hosted
    steps:
      - name: Run retrieval eval
        run: python eval/run_retrieval.py --golden eval/golden_set.json
      
      - name: Check regression
        run: python eval/check_regression.py --threshold 0.85
      
      - name: Update Qdrant (if passed)
        if: success()
        run: python scripts/index_kb.py --collection knowledge_base
```

При каждом изменении KB:
1. CI прогоняет golden set через retrieval pipeline
2. Сравнивает Recall@5 с порогом (85%)
3. Если упал — блокирует публикацию, показывает какие вопросы сломались
4. Если прошёл — обновляет Qdrant

### Сравнение с Chatme

Прогнать одинаковый набор из 100 вопросов через оба бота. Сравнить:
- Task Success Rate (вопрос решён без эскалации)
- Составные вопросы (Chatme выбирает один интент, новый бот отвечает на все)
- Актуальность (Chatme может отвечать устаревшей информацией)

Результат — числовой аргумент для ГД при решении о переносе трафика.

## 10. Стек

| Компонент | Технология | Обоснование |
|---|---|---|
| Backend | **FastAPI** | Async, webhook-ы, команда знает Python |
| Оркестрация | **LangGraph** | Граф состояний, checkpoint, replay, расширяемость |
| LLM API | **Cloud.ru Evolution Foundation Models** | OpenAI-compatible `/v1/chat/completions`, Bearer API key, без Sber OAuth |
| LLM simple/judge | **ai-sage/GigaChat3-10B-A1.8B** | Типовые вопросы вроде регистрации на форум, экономичный judge |
| LLM complex/analyzer | **GigaChat/GigaChat-2-Max** | Нетиповые, составные, путаные запросы; Cloud.ru model id задаётся в `CLOUD_RU_MODEL_COMPLEX` |
| Embedding + Sparse | **bge-m3** | Dense + sparse из одной модели, хороший русский, локально |
| Reranker | **bge-reranker-v2-m3** | Локально, без API, хороший русский |
| Векторная БД | **Qdrant** | Hybrid search, metadata filtering, lightweight |
| Реляционная БД | **PostgreSQL** | Логи, память, версии, админка |
| Кэш + сессии | **Redis** | TTL, быстрый, stateless |
| PII-маскирование | **Natasha + regex** | Проверено в HDE→n8n пайплайне |
| Админ-панель | **React** (или Streamlit для MVP) | Минимальный UI для редакторов |
| Развёртывание | **Docker Compose** | Один сервер, воспроизводимость |
| Сервер | **Selectel** | 152-ФЗ, опыт |
| CI/CD | **GitHub Actions** | KB-индексация, eval pipeline, тесты |

## 11. Стоимость (детализированная)

При ~1200 тикетов/мес, cache hit rate 35%, каскад внутри Cloud.ru:
типовые запросы → `ai-sage/GigaChat3-10B-A1.8B`, нетиповые/complex →
`GigaChat/GigaChat-2-Max`.

Тариф Cloud.ru Evolution Foundation Models для Max: входные токены — 569.34 ₽/млн,
генерируемые токены — 569.34 ₽/млн, контекст до 131K токенов. Это дешевле прямого
Sber GigaChat API при 650 ₽/млн. В архитектуре важно правило интеграции:
OpenAI-compatible endpoint + Bearer `CLOUD_RU_API_KEY`, без OAuth и без `GIGACHAT_*`
переменных.

| Статья | Расчёт | Сумма/мес |
|---|---|---|
| **Cloud.ru LLM API** | Analyzer/complex через `GigaChat/GigaChat-2-Max`, simple/judge через 10B | Max: 569.34 ₽/млн входных и 569.34 ₽/млн выходных токенов |
| **Embedding (bge-m3)** | Локально | 0 ₽ |
| **Reranker (bge-reranker)** | Локально | 0 ₽ |
| **Сервер Selectel** | 4 vCPU, 16 GB RAM, 100 GB SSD | ~3000 ₽ |
| **Резервное копирование** | | ~300 ₽ |
| **Мониторинг** | | ~200 ₽ |
| **Итого без LLM API** | Инфраструктура без переменной стоимости токенов | **~3500 ₽ + Cloud.ru usage** |

Экономия достигается не переключением на другой Sber/OAuth-провайдер, а за счёт semantic cache,
RAG-фильтрации, коротких промптов, отказа от LLM при низкой уверенности и локальных bge-моделей.

## 12. Фазы разработки

### Phase 1: Фундамент (2 недели)

**Неделя 1:**
- Извлечь KB seed из `Новый бот Росмол .xlsx` и DOCX-источников → `knowledge_base_seed.json`
- Поднять Qdrant, загрузить чанки с bge-m3 (dense + sparse)
- Поднять PostgreSQL (таблицы: request_traces, user_memory, chunk_versions)
- Поднять Redis
- Docker Compose для всего стека

**Неделя 2:**
- Написать Query Analyzer промпт, прогнать на 30 реальных вопросах
- Собрать retrieval pipeline (filter → hybrid search → rerank)
- Собрать golden set (50 вопросов из HDE)
- Прогнать eval: Retrieval Recall@5

**Результат:** `python ask.py "Мне 17 лет, хочу на Машук, кто платит за дорогу?"` → top-5 чанков с scores + анализ запроса.

### Phase 2: Генерация и оркестрация (2 недели)

**Неделя 3:**
- LangGraph: граф с нодами analyze → retrieve → rerank → generate → verify → respond
- Response Generator + system prompt + Cloud.ru LLM client
- Verifier (regex + confidence + LLM-judge)
- Семантический кэш

**Неделя 4:**
- Session Manager (Redis, мультитурн)
- Долгосрочная память (PostgreSQL)
- Response Logger (полный trace)
- Расширить golden set до 100 вопросов, полный eval

**Результат:** HTTP API — `POST /ask` → JSON с ответом, источниками, trace.

### Phase 3: Каналы, админка, продакшн (2 недели)

**Неделя 5:**
- Channel Adapters (VK, MAX, HDE webhook)
- Security Layer (PII Natasha, profanity, safety, rate limiter)
- Эскалация в HDE (кастомные поля ID=23, 25, 29)
- Админ-панель: CRUD для чанков, фильтры, публикация

**Неделя 6:**
- Eval CI pipeline (GitHub Actions)
- Нагрузочное тестирование (50 concurrent)
- Мониторинг: latency, error rate, escalation rate, cache hit rate
- Дашборд качества в админке

**Результат:** Полноценный MVP на реальном трафике, параллельно с Chatme.

### Phase 4: Шлифовка (2-4 недели, после запуска)

- Калибровка порогов reranker на реальных данных
- Оптимизация промптов по результатам traces
- KB gap detection (автоматический отчёт из логов: темы без чанков)
- Расширение KB: положения форумов, памятки, новые форумы
- YouNote интеграция
- A/B тест: новый бот vs Chatme на части трафика

## 13. Чего здесь намеренно НЕТ

- **Мультимодальность (голос, изображения):** не приоритет, не влияет на архитектуру ядра.
- **Автоматическое предложение новых KB-чанков из тикетов:** фича поверх рабочей системы, Phase 5+.
- **Enterprise Knowledge Studio:** админка покрывает 95% потребностей. Полноценная CMS — если будет 10+ редакторов и workflow согласования.
- **Кросс-форумные рекомендации («тебе может подойти ещё Бирюса»):** можно добавить как отдельную ноду в LangGraph, но после стабилизации основного pipeline.
