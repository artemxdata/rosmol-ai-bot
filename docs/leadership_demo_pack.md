# Пакет демонстрации AI-бота Росмолодёжи

## Короткий вывод

Бот уже можно показывать как рабочий продуктовый контур, а не как MVP в терминале. У нас есть ядро RAG, тестовый HDE/VK-контур, админка знаний, Yonote как read-only источник актуальной базы, отчёты качества, trace, PII masking, safety escalation и защита от ответов вне источников.

Честная формулировка для руководства: текущие calibrated-тесты показывают высокий уровень закрытия без оператора, но это не обещание 100% на всех будущих новых вопросах. Реальная production-конверсия будет расти через еженедельную калибровку базы знаний по новым деперсонализированным тикетам.

## Что именно показываем

1. Бот отвечает по базе знаний и Yonote-источникам, а не “из головы”.
2. Составные вопросы разбираются на несколько тем и закрываются несколькими источниками.
3. Если данных нет, бот не выдумывает: даёт scope-note, уточнение или controlled escalation.
4. Опасные темы уходят специалисту.
5. Админка позволяет править чанки и сразу обновлять RAG.
6. Ops report показывает стоимость, latency, cache hit, эскалации и проблемные темы.
7. Yonote подключён безопасно: только чтение, без изменения чужой базы.

## Что сказать про качество

Формулировка:

> На подготовленных наборах бот показывает высокий процент закрытия без оператора, особенно после подключения Yonote. Но мы не продаём это как магические 100%. Главная ценность архитектуры в том, что качество управляемое: если вопрос не закрывается, мы видим причину, источник, тему и можем точечно пополнить базу.

Что не говорить:

- “Бот всегда ответит на всё”.
- “Операторы больше не нужны”.
- “Можно сразу включать на все каналы”.
- “Yonote бот будет менять сам”.

Что говорить:

- “Бот снижает нагрузку на операторов по типовым и хорошо покрытым вопросам”.
- “Вопросы вне базы не превращаются в галлюцинации”.
- “Конверсию можно повышать продуктовым циклом: тикеты -> пробелы -> база -> eval -> релиз”.
- “Production-пилот должен идти через тестовый канал и метрики”.

## Матрица рисков

| Риск | Что будет | Как закрыли |
| --- | --- | --- |
| Устаревшая база | Бот даст старый ответ | Yonote read-only sync, админка, validation, reindex |
| Новый вопрос вне базы | Бот не сможет закрыть обращение | Scope-note/уточнение/эскалация + weekly gap analysis |
| Галлюцинация | Ответ без источника | Source-only/RAG guard, cited_sources, verifier |
| ПДн в LLM или Git | Утечка данных | PII masking, `data/private`, `.gitignore`, sanitized eval |
| Опасная тема | Бот начнёт советовать сам | Safety escalation без LLM-самодеятельности |
| HDE бан по лимиту | Ответы перестанут уходить в канал | Локальные тесты, rate-limit awareness, HDE только для smoke |
| Старый бот отвечает параллельно | Непонятно, кто дал ответ | Тестовый канал, правила диспетчера, trace |
| Дорогие LLM-вызовы | Рост расходов | Source_chunk first, Max только для сложных случаев, cost trace |
| Ошибка редактора в админке | Плохой текст попадёт в RAG | Validation, точечный reindex, git/backup как rollback |

## Еженедельный процесс улучшения

1. Выгрузить деперсонализированные HDE-тикеты за неделю.
2. Прогнать анализатор: темы, подтемы, причины эскалаций, вопросы без ответа.
3. Сравнить с RAG/Yonote: есть ли источник, правильный ли он, хватает ли чанка.
4. Разделить gaps:
   - уже есть источник, но retrieval не нашёл;
   - источника нет, нужен текст от команды;
   - тема вне зоны бота;
   - safety/operator-only.
5. Для недостающих источников поставить задачу контент-владельцу или копирайтеру.
6. Обновить Yonote или админку KB.
7. Пересобрать RAG: preview -> apply -> validation -> index.
8. Прогнать eval и smoke.
9. Зафиксировать метрики: conversion without operator, escalation rate, source coverage, hallucination rate, latency, cost.

## Что ещё имеет смысл делать до презентации

- Держать demo set стабильным и не менять его прямо перед встречей.
- Сделать свежий smoke утром перед показом.
- Проверить 5-10 живых вопросов руками.
- Показать не только ответы, но и управляемость: trace, источники, админку, ops report.

## Что уже нет смысла делать до презентации

- Гнаться за 100% на тех же вопросах: это создаёт иллюзию качества.
- Переключать всё на Max: качество базы важнее модели.
- Подключать широкие production-правила HDE до пилота.
- Делать автономного агента, который сам пишет в Yonote. Пока только read-only.
- Начинать рассылки: это отдельный продуктовый модуль.

## Решения, которые нужно получить

1. Кто владелец контента и Yonote-разделов.
2. Какой тестовый канал считаем пилотным.
3. Какой SLA ответа и допустимая доля эскалаций на пилоте.
4. Как часто выгружаем деперсонализированные тикеты.
5. Кто принимает новые ответы перед публикацией.
6. Когда разрешаем переход от тестового канала к production.
