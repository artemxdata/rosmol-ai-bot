# Контракт миграции legacy NLU

## Назначение

Старый NLU используется как согласованный источник структуры ответа и сервисных формулировок.
Он не является источником актуальных фактов. Канонические сервисные реплики находятся в
`data/response_contract_v1.json`, а структурное покрытие старого дерева — в
`data/legacy_nlu_migration_matrix_v1.json`.

Исходный конфигурационный файл не входит в репозиторий и не является runtime-зависимостью.
Матрица хранит только названия NLU-контуров, структурные идентификаторы веток, количества узлов и
категории миграции. Тексты фактических ответов и интеграционные настройки в неё не переносятся.

## Зафиксированная baseline

- Найдено ровно 42 NLU-корня.
- От них достижимы ровно 762 ответных context-узла.
- Ответным считается context-узел с входом `bot_message`.
- Обход начинается от NLU-корня и останавливается перед вложенным NLU- или LLM-узлом.
- Пересечений ответных узлов между корнями нет.
- Внутри корня каждый ответный узел относится ровно к одной непосредственной ветке первого
  уровня.

Имена механически нормализованы только удалением внешних пробелов. Содержательная редактура имён
в этой baseline не выполнялась.

## Категории миграции

| Категория | Правило |
|---|---|
| `exact_static` | Использовать утверждённую сервисную реплику из versioned response contract |
| `yonote_template` | Сохранить назначение и порядок ответа, а динамические поля заполнить только из опубликованного Yonote snapshot |
| `current_safety_policy` | Использовать текущие правила безопасности, off-topic и контролируемой эскалации вместо конфликтующей legacy-логики |
| `deprecated` | Не переносить старую техническую или резервную ветку в новый runtime |

`yonote_template` не разрешает копировать старые даты, условия, ссылки или иной фактический
текст. Если опубликованного подтверждения не хватает, применяется уточнение или контролируемая
эскалация.

## Однозначность покрытия

Единица разбиения — непосредственная ветка NLU-корня. В каждом контуре заданы две независимые
partition: migration disposition и внутренний `response_profile`. Для каждой partition хранится
значение по умолчанию и список исключений по структурному `branch_slot_index`. Исключение профиля
дополнительно хранит только число покрытых ответных узлов, без legacy-текста. Так как ответные
узлы веток не пересекаются, каждый из 762 узлов получает ровно одну migration-категорию и ровно
один из 13 разрешённых `response_profile`.

Суммарное распределение:

- `exact_static` — 6;
- `yonote_template` — 710;
- `current_safety_policy` — 1;
- `deprecated` — 45.

Сумма равна 762. Контуры мероприятий и грантов преимущественно переходят в
`yonote_template`. Общий сервисный контур намеренно смешанный: утверждённые реплики остаются
статическими, фактические ответы получают данные из Yonote, конфликтующая policy-ветка подчиняется
текущим правилам, а резервная ветка выводится из эксплуатации.

Распределение по внутренним профилям:

- `dates` — 38;
- `application` — 64;
- `eligibility` — 65;
- `documents` — 131;
- `selection_status` — 65;
- `program` — 42;
- `travel` — 56;
- `accommodation` — 17;
- `food` — 23;
- `accessibility` — 18;
- `grants` — 29;
- `technical` — 40;
- `generic` — 174.

Сумма также равна 762. Профиль классифицировался только по структурному назначению
непосредственной legacy-ветки. Старые ответы и factual-поля для этого не переносились.

## Граница изменения

Матрица является review-артефактом и тестируемым контрактом миграции. Она сама не является
runtime routing table и не меняет retrieval, prompts, базу знаний или канальные payload.
Runtime выбирает те же 13 профилей своей проверяемой логикой; матрица служит доказательством,
что ни одна legacy-ветка не потеряна при миграции.
